# Проверка условий договоров поставки

Локальный прототип для специалиста по закупкам. Загружает несколько TXT-файлов, связывает документы по номеру договора из текста, показывает действующие сумму и срок поставки на выбранную дату и открывает исходный абзац для каждого значения. В корне находятся два самостоятельных проекта: Go API в `back/` и React + TypeScript в `front/`.

## Запуск

Нужны Docker Engine и Docker Compose. Из корня проекта:

```sh
docker compose up --build
```

Откройте http://localhost:8088. Выберите все шесть файлов из `documents/`, оставьте дату `2026-03-10` и нажмите «Проверить документы». Для остановки: `docker compose down`.

Для разработки без Docker нужны Go 1.24+ и Node.js 22+:

```sh
cd back && go run ./cmd/api
```

В другом терминале:

```sh
cd front && npm install && npm run dev
```

Откройте адрес, который напечатает Vite (обычно http://localhost:5173). API доступен на `http://localhost:8080`; Vite проксирует `/api` к нему. Секреты и платный API не нужны.

## Сценарий и ожидаемые ответы

| Договор | Сумма | Срок поставки на 10.03.2026 | Примечание |
|---|---:|---|---|
| STN-101 | 1 380 000 ₽ | 30.04.2026 | По подписанному соглашению № 1; проект № 2 не применяется |
| STN-102 | 840 000 ₽ | 20.03.2026 | Перенос на 27.03.2026 предложен письмом, но не согласован |
| STN-103 | нет данных | 30.04.2026 | Спецификация с ценой отсутствует; бюджетный лимит не считается ценой |

Фильтр «Поставка до даты» с датой `2026-04-01` выводит STN-102 и отметку о несогласованном переносе. Нажатие на значение или предложение открывает его файл и выделяет точный абзац. Измените сумму или срок в TXT и загрузите файлы заново: результат пересчитывается из текста.

## API

`POST /api/analyze` принимает `multipart/form-data`: повторяемое поле `files` с TXT и обязательное `as_of` в формате `YYYY-MM-DD`. В интерфейсе дата проверки из задания уже выбрана. API возвращает `contracts`, `documents`, `warnings`, `as_of`. У поля есть `value`, `changed` и `evidence` с `document_id`, `file_name`, `paragraph_id`, `quote`. Пустое значение означает «нет данных». `GET /api/health` возвращает состояние сервиса. Ошибки ввода возвращаются как JSON `{"error":"..."}` с HTTP 400. Лимиты: 100 файлов, 1 МБ на файл, 10 МБ на запрос.

Пример прямого запроса:

```sh
curl -F as_of=2026-03-10 -F files=@documents/01_contract.txt -F files=@documents/02_amendment_signed.txt http://localhost:8088/api/analyze
```

## Краткая продуктовая записка

**Пользователь.** Закупщик, который быстро сверяет действующие условия поставки и при необходимости подтверждает их первоисточником.

**Пять вопросов клиенту перед развитием:**

1. Какие виды договоров и формулировки встречаются чаще всего?
2. Кто и как подтверждает статус подписания и дату вступления соглашения в силу?
3. Нужно ли учитывать частичные поставки и отдельные цены/сроки по позициям спецификации?
4. Какова допустимая доля случаев, отправленных на ручную проверку, и цена неверного ответа?
5. Какие права доступа и сроки хранения исходных документов обязательны?

**Допущения.** Учебные TXT имеют UTF-8, один основной договор на номер, условия находятся в нумерованных строках общего формата. Изменение действует только после подписания обеими сторонами к дате проверки и наступления явно указанной даты вступления в силу. Письмо и проект отображаются как предложения. Дата и имя файла не задают приоритет. При отсутствии суммы показывается «нет данных». При конфликте изменений или невозможности извлечь новое условие показывается ручная проверка.

**Две метрики:** (1) доля корректных ответов по сумме и сроку, подтвержденных человеком по цитате; (2) медианное время от загрузки до проверки закупщиком четырех вопросов.

**Архитектура.** React отправляет TXT в Go API. Go выделяет строки-абзацы, классифицирует документы, извлекает поля и хранит точную цитату с ID абзаца. Затем применяет подписанные соглашения по дате вступления в силу и возвращает таблицу и предложения. Данные остаются в памяти на время запроса; базы данных нет.

Frontend организован по FSD: `app` — точка сборки и общие стили; `pages/contract-check` — композиция экрана; `features` — загрузка и фильтр; `entities` — договор и документ; `shared` — общий тип ссылки на источник. UI разбит на компоненты с локальными SCSS-модулями. Импорты между слоями используют alias `@/`, который ведет в `front/src` и настроен в TypeScript и Vite. Backend разделен на `cmd/api` (запуск), `internal/httpapi` (маршруты, валидация, DTO), `internal/analysis` (сценарий и правила) и `internal/domain` (модель). HTTP-слой зависит от интерфейса `Analyzer`, поэтому адаптеры БД и кэша можно добавить отдельными пакетами без переноса правил в обработчики. Микросервисы для этого объема не требуются.

**Три решения и компромиссы:**

1. Правила и регулярные выражения вместо LLM внутри приложения: быстрый бесплатный и воспроизводимый запуск, но новые формулировки потребуют расширения правил.
2. Привязка результата к исходной строке: проверка значения занимает один клик, но многострочные абзацы и сложная верстка пока не поддержаны.
3. Применение только подтвержденных изменений: меньше ложных обновлений, но неполные сведения о статусе требуют ручной проверки.

**При 100 000 документов и правах доступа** понадобятся постоянное хранилище файлов и извлеченных фактов, очередь фоновой обработки, индексы по номеру договора и датам, контроль версий и журнал изменений. Проверка прав должна выполняться на сервере при поиске, выдаче факта и открытии цитаты; ссылки на источник не должны обходить ACL.

**Следующие улучшения по приоритету:** (1) расширить и измерить извлечение на реальном наборе документов с разметкой ошибок; (2) добавить поток ручной проверки спорных случаев и сохранение решений; (3) добавить хранение, поиск и права доступа.

## Проверка и ограничения

`cd back && go test ./...` проверяет исходные шесть файлов, цитаты, отсутствие цены, предложения, изменение суммы, добавление нового договора, порядок загрузки, спорные подписанные изменения и HTTP-ответ. `cd front && npm run typecheck` проверяет типы; `npm run build` также собирает React и SCSS. Формат извлечения ограничен учебными и близкими к ним русскоязычными TXT: произвольные договоры, OCR, PDF/DOCX, частичные поставки и сложные цепочки противоречащих соглашений не поддержаны. Прототип не предназначен для юридически значимого решения без проверки человеком.

## Отчет об использовании ИИ

Инструмент разработки: OpenAI Codex. Характерные запросы из работы: «Сделаем простенький бек на Go + визуал на React, все собери в докер»; «Фронт давай на TypeScript ... FSD ... модульный SCSS ... DTO вынести отдельно»; «Еще раз изучи ТЗ и проверь, что все ему соответствует». При первой реализации регулярное выражение суммы не учитывало число прописью между цифрами и словом «рублей»: тесты показали пустую сумму. Выражение исправлено и повторно проверено тестами.

Фактические затраты на первую версию, реорганизацию и аудит: около 35 минут. Оставшаяся проверка: запустить `docker compose up --build` и пройти сценарий в браузере в среде с доступом к Docker-сокету. В текущей среде Go-тесты, сборка frontend с TypeScript и SCSS и проверка конфигурации Compose прошли; Docker-сокет заблокирован.
